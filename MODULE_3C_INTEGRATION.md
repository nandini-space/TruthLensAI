# TruthLensAI Module 3C Integration Contract

## Scope

**Production Telegram update owner: n8n.** The Python package under
module_3c/telegram_bot is an offline prototype/reference implementation and
must not poll the same bot token as the n8n Telegram Trigger.

Module 3C is the Telegram/n8n adapter. It submits user content to the existing
HTTP API, translates API responses to the stable envelope below, and renders
that envelope in Telegram. It does not import backend classes, run detection,
extract IOCs, enrich intelligence, create incidents, generate reports, or
execute response actions.

The backend supports optional shared-service authentication. When
`TRUTHLENSAI_API_KEY` is configured, n8n must send it as
`X-TruthLens-API-Key` on every API call other than `/health`; store it in an
n8n credential, never in a workflow export. This is a service-to-service
control, not user authorization. Before public exposure, deploy TLS, network
restrictions, gateway-level rate limits, and Telegram webhook verification.

## Existing API surface

### Module 1 detection routes

| Method | URL | Request | Success | Errors |
|---|---|---|---|---|
| `GET` | `/health` | none | `200` health JSON | none documented |
| `POST` | `/scan/text` | JSON: `{ "text": "..." }` | `200` detection `ScanResult` | `422`, `500` |
| `POST` | `/scan/url` | JSON: `{ "url": "https://..." }` | `200` detection `ScanResult` | `422`, `500` |
| `POST` | `/scan/image` | multipart field `file` (PNG/JPEG/WEBP) | `200` detection `ScanResult` | `400`, `413`, `422`, `500` |
| `POST` | `/scan/audio` | multipart field `file` (WAV/MP3/M4A/FLAC) | `200` detection `ScanResult` | `400`, `413`, `422`, `500` |
| `POST` | `/scan/video` | multipart field `file` (MP4/AVI/MOV/MKV/WEBM) | `200` detection `ScanResult` | `400`, `413`, `422`, `500` |
| `POST` | `/scan/multimodal` | multipart/form fields `text`, `url`, `image`, `audio`, `video`; at least one | `200` fused detection `ScanResult` | `400`, `413`, `422`, `500` |

The exposed detection result is `backend.detection.schemas.ScanResult`: it
contains `scan_id`, `input_type`, nullable `risk_score`/`confidence`,
`severity` (`unknown`, `low`, `moderate`, `high`, `critical`), `threat_type`,
`signals`, `explanation`, `recommendation`, `entities`, `metadata`, and
`created_at`.

### Module 2 investigation routes

| Method | URL | Request | Success | Errors |
|---|---|---|---|---|
| `POST` | `/api/module2/investigate` | canonical `backend.models.schemas.ScanResult` | `200` `Module2Result` | `409`, `422`, `500`, `503` |
| `GET` | `/api/module2/investigations/{scan_id}` | UUID path parameter | `200` persisted `Module2Result` | `404`, `422`, `503` |
| `GET` | `/api/module2/investigations?limit=20&offset=0` | pagination query parameters | `200` `{items, limit, offset, count}` | `422`, `503` |

`Module2Result` contains the nested canonical scan, normalized indicators,
provider and aggregate intelligence, evidence pack, incident, forensic report,
STIX bundle, response decisions, and dry-run action records. An incident has
`incident_id`, `scan_id`, detection severity/risk/confidence, lifecycle status
(`open`, `investigating`, `resolved`), and evidence reference. A forensic report
is nested in the investigation response; it has `report_id`, `incident_id`,
`scan_id`, analysis, recommendation, indicators, intelligence, evidence, and
incident snapshots.

## Important current compatibility gap

The Module 1 HTTP routes return `backend.detection.schemas.ScanResult`, but
Module 2 accepts the separate canonical
`backend.models.schemas.ScanResult`. Their fields and enum values differ (for
example, `input_type` versus `modality`, `entities` versus
`extracted_entities`, and `created_at` versus `timestamp`). No HTTP endpoint
currently converts one into the other.

**TODO / REQUIRED FROM MODULE 1 OR MODULE 2:** provide a documented server-side
canonicalization/handoff endpoint or make the Module 1 routes emit the canonical
contract. Module 3C/n8n must not construct a Module 2 request by guessing this
mapping. Until this is delivered, Module 3C can display Module 1 scan results,
but cannot safely start a Module 2 investigation from a Module 1 HTTP response.

## Telegram → n8n input

n8n owns Telegram update parsing and creates a request ID. It should retain
Telegram-specific identifiers only in its own workflow state, not send them to
the backend unless a future authenticated backend contract requires them.

```json
{
  "request_id": "UUID generated by n8n",
  "telegram": { "chat_id": "string", "message_id": "string" },
  "source": {
    "type": "text",
    "value": "message text",
    "file_name": null,
    "mime_type": "text/plain"
  }
}
```

`type` is one of `text`, `url`, `image`, `audio`, or `video`. For media,
`value` is a workflow-local file reference or filename, never a base64 copy of
the media; n8n sends the downloaded file as multipart `file`.

## n8n → backend requests

n8n selects an existing Module 1 route by `source.type`: JSON for text/URL and
multipart uploads for media. It must preserve the backend's success/error body
unchanged until it maps it to the normalized envelope. `POST /scan` does not
exist and must not be called.

Only after the compatibility TODO above is implemented may n8n submit the
returned **canonical** scan to `POST /api/module2/investigate`. The investigation
request has no `request_id`; n8n correlates the response through workflow state
and the backend `scan_id`.

## Stable Module 3C normalized response

This is a Module 3C adapter contract, not a new backend endpoint or a duplicate
of either backend model. Nullable values mean the backend did not assess or did
not provide that artifact. n8n should version this envelope independently and
keep unknown backend fields out of it unless the contract is deliberately
extended.

```json
{
  "contract_version": "1.0",
  "request_id": "UUID generated by n8n",
  "status": "success",
  "source": {
    "type": "text",
    "value": "message text or safe media reference"
  },
  "scan": {
    "scan_id": "UUID",
    "risk_score": 82.0,
    "severity": "high",
    "threat_type": "phishing",
    "confidence": 0.91,
    "signals": [
      { "id": "credential_request", "summary": "Credential request detected", "source": "text_detector" }
    ],
    "explanation": "...",
    "recommendation": "..."
  },
  "threat_intelligence": {
    "available": false,
    "status": "not_requested",
    "iocs": [],
    "enrichment": []
  },
  "incident": {
    "incident_id": null,
    "status": null,
    "report_id": null
  },
  "actions": [],
  "capabilities": {
    "why_suspicious": true,
    "what_to_do": true,
    "full_report": false,
    "feedback": false
  }
}
```

Mapping rules:

- A Module 1 result supplies `scan` from its score, severity, threat type,
  confidence, signals, explanation, and recommendation. Preserve `null` score
  or confidence; do not turn an unassessed result into benign.
- A successful Module 2 result supplies `scan` from nested `scan_result`,
  `iocs` from `indicators`, `enrichment` from aggregate
  `threat_intelligence`, incident/report IDs from `incident` and
  `forensic_report`, and `actions` from `action_records`.
- Module 2 `unavailable` or `error` intelligence is represented as unavailable,
  never benign. All current action records are dry-run and `executed=false`.
- `request_id` is n8n correlation data, while `scan_id` is the backend identity.

## Error envelope

Module 1 business errors have `{ "detail": { "error": "...", "detail":
"..." } }`; Module 2 business errors have `{ "detail": "..." }`; FastAPI
validation errors have a `detail` array. n8n normalizes all of them without
exposing internal exception text:

```json
{
  "contract_version": "1.0",
  "request_id": "UUID generated by n8n",
  "status": "error",
  "error": {
    "code": "validation_error|unsupported_file_type|upload_too_large|detection_failed|investigation_unavailable|duplicate_investigation|not_found|backend_error",
    "message": "Safe user-facing message.",
    "retryable": false
  }
}
```

Use `retryable: true` for backend `503` and transient `500` failures. Do not
return provider credentials, backend stack traces, Telegram tokens, or raw
untrusted error details to Telegram.

## n8n → Telegram response

n8n renders the normalized envelope rather than backend JSON directly. The
initial message should show threat type, severity, risk score when present,
confidence when present, explanation, recommendation, and an intelligence
availability indicator. It should attach `request_id` and `scan_id` only in
callback data/workflow state, not necessarily visible message text.

```json
{
  "chat_id": "string",
  "text": "Risk: HIGH (82/100)\nType: phishing\nRecommendation: Do not share credentials.",
  "inline_keyboard": [[
    { "text": "Why suspicious?", "callback_data": "opaque callback token" },
    { "text": "What should I do?", "callback_data": "opaque callback token" }
  ]]
}
```

Use compact opaque callback tokens stored by n8n; do not place raw message
contents, credentials, or large reports in Telegram callback data.

## Telegram action contract

The workflow resolves the opaque callback to this internal action request:

```json
{
  "contract_version": "1.0",
  "action": "WHY_SUSPICIOUS",
  "request_id": "UUID generated by n8n",
  "scan_id": "UUID or null",
  "incident_id": "UUID or null"
}
```

| Action | Current behavior | Backend call |
|---|---|---|
| `WHY_SUSPICIOUS` | Display stored normalized signals and explanation. | None |
| `WHAT_TO_DO` | Display stored normalized recommendation. | None |
| `FULL_REPORT` | Display/format the already returned forensic report, or retrieve it through `GET /api/module2/investigations/{scan_id}` only when persistence is configured. | Optional existing GET |
| `MARK_SAFE` | Unsupported. Do not alter a scan, intelligence result, or incident. | **TODO / REQUIRED FROM MODULE 1 OR MODULE 2** |
| `REPORT_SCAM` | Unsupported. Do not create or modify an incident. | **TODO / REQUIRED FROM MODULE 2** |
| `CORRECT` | Unsupported backend feedback capability. | **TODO / REQUIRED FROM MODULE 1 OR MODULE 2** |
| `INCORRECT` | Unsupported backend feedback capability. | **TODO / REQUIRED FROM MODULE 1 OR MODULE 2** |

`FULL_REPORT` is enabled only if the normalized response includes a report or a
persisted investigation can be retrieved by `scan_id`. Current retrieval is
read-only and may return `503` when persistence is unavailable.

## Missing endpoints and capabilities

These are not implemented and must not be faked by Module 3C:

| Requested capability | Current status |
|---|---|
| `POST /scan` | Missing; use the modality-specific Module 1 routes. |
| `GET /scan/{request_id}` | Missing; backend has no n8n `request_id` store. |
| Canonical Module 1 → Module 2 handoff | Missing; required before automated investigation. |
| `GET /incidents/{incident_id}` | Missing; only lookup by persisted `scan_id` exists. |
| `GET /incidents/{incident_id}/report` | Missing; report is nested in `Module2Result`. |
| `POST /incidents/{incident_id}/actions` | Missing and inappropriate for current dry-run-only response behavior. |
| Feedback / mark-safe / report-scam mutations | Missing. |
| Backend authentication/authorization | Optional shared service key exists; deployment still requires network and webhook controls. |

## Communication flow

```text
Telegram update -> n8n request envelope -> existing Module 1 scan route
    -> Module 3C normalized response -> Telegram result and informational buttons

canonical backend handoff (TODO) -> POST /api/module2/investigate
    -> normalized enriched result -> Telegram report/intelligence presentation
```

This keeps Module 3C coupled only to HTTP payloads and its own stable envelope;
it never relies on Module 1/2 private helpers or database tables.
